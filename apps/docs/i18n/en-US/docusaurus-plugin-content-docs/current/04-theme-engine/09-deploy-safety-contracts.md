# Deploy Safety Contracts

## What it is

A **token contract** is a structural snapshot of the output generated by the Aplica Theme Engine: token paths and their types, without the values. It works as the "API signature" of the token package — stable across patch and minor releases, and it only changes when paths are added, removed or renamed.

The mechanism solves a classic problem in distributed design system architectures: when the Theme Engine config repository renames a token, the component library keeps using the old name — and nothing detects the break before the deploy reaches production.

---

## Why values are not enough

A value change (`#265ed9` → `#1a4fc2`) breaks no component. Removing or renaming a path (`color.brand.branding.first.default.background` → `color.brand.primary.default.bg`) breaks every component that references the old name through a CSS var or JS token.

The contract captures **structure**, not value. That makes it stable to commit in the component library and reliable as a CI signal.

---

## The two repositories

The flow assumes the recommended two-repo architecture:

```
Theme Engine config repo        Component library repo
(owns config/ + tokens)    →   (installs the published package)
```

Each repo has a distinct responsibility in the contract cycle:

| Repo | Action | When |
|------|--------|------|
| Theme Engine config | `contracts:generate` | After `build`, before `npm publish` |
| Component library | `contracts:diff` in CI | On PRs that update the token package |

---

## Contract file structure

```json
{
  "version": "3.16.0",
  "generatedAt": "2026-05-09T...",
  "brand": "aplica_blue_sky",
  "paths": {
    "color.brand.branding.first.default.background": "color",
    "color.brand.branding.second.default.background": "color",
    "color.interface.feedback.solid.danger.default.normal.background": "color",
    "typography.heading.headline_1.fontFamily": "string",
    "border.radii.medium": "dimension",
    "dimension.semantic.medium": "dimension"
  }
}
```

Only paths and types. Values never enter the contract.

---

## Generating the contract — `contracts:generate`

Run it in the config repository after the build:

```bash
# Primary brand (detected from themes.config.json)
theme-engine contracts:generate

# A specific brand
theme-engine contracts:generate --brand aplica_slate

# All brands at once
theme-engine contracts:generate --all
```

**Output:** `dist/contracts/<brand>-contract.json`

The file ships in the NPM package together with `dist/` and is available at `node_modules/@aplica/aplica-theme-engine/dist/contracts/` in every library that installs the package.

---

## Comparing contracts — `contracts:diff`

Run it in the component library, in CI, after installing a new version of the token package:

```bash
# Compare the local contract against the one shipped in the installed package
theme-engine contracts:diff --contract ./contracts/aplica_blue_sky-contract.json

# Also write a report file, besides the terminal log
theme-engine contracts:diff \
  --contract ./contracts/aplica_blue_sky-contract.json \
  --output ./contracts/diff-report.json
```

The engine automatically locates the package contract at `node_modules/@aplica/aplica-theme-engine/dist/contracts/<brand>-contract.json`.

---

## The three outcomes

| Outcome | Condition | Exit code | Recommended action |
|---------|-----------|-----------|--------------------|
| ✅ **Green** | No structural change | `0` | CI passes silently |
| ⚠️ **Alert** | New paths added (additive, non-breaking) | `0` with a warning | CI passes — the dev updates the local contract |
| ❌ **Error** | Paths removed or types changed (breaking) | `1` | CI blocks — review required |

**Error** happens when a path that exists in the library contract disappears or changes type in the new package. Components that reference that path will break at runtime.

**Alert** means the package gained new paths the library has not mapped yet. The local contract should be updated to reflect the newly available surface.

---

## GitHub Action template

The package ships a ready-made workflow template. Copy it into the component library:

```bash
cp node_modules/@aplica/aplica-theme-engine/templates/github-actions/contracts-check.yml \
   .github/workflows/contracts-check.yml
```

The workflow runs `contracts:diff` on PRs that update `package.json` and blocks the merge on **Error**.

---

## Setting up the initial contract in a library

The first time you adopt contracts in an existing library:

```bash
# 1. In the config repo — generate the contract for the current version
theme-engine contracts:generate

# 2. Copy the contract into the library
cp <engine-config-path>/dist/contracts/aplica_blue_sky-contract.json \
   <library-path>/contracts/aplica_blue_sky-contract.json

# 3. Commit the contract in the library
git add contracts/aplica_blue_sky-contract.json
git commit -m "chore: add initial token contract baseline"
```

From then on, every token package update goes through `contracts:diff` in CI.

---

## Updating the contract after an Alert

When CI reports **Alert** (new paths), update the local contract to take in the new surface:

```bash
# Generate the updated contract in the config repo and republish
theme-engine contracts:generate && npm publish

# In the library, after installing the new version:
cp node_modules/@aplica/aplica-theme-engine/dist/contracts/aplica_blue_sky-contract.json \
   ./contracts/aplica_blue_sky-contract.json
git add contracts/aplica_blue_sky-contract.json
git commit -m "chore: update token contract to include new paths"
```

## Audience

| Role | What to do |
|------|-----------|
| **Design Engineer (N3)** | Sets up `contracts:generate` in the engine config repo's publish pipeline. Understands what each outcome means for the library. |
| **Platform engineer** | Adds `contracts:diff` to the component library's CI. Manually reviews releases that produce **Error**. |
| **System Designer (N2)** | Does not run contracts directly, but should know that renaming a token causes **Error** in libraries that already consume it. |
