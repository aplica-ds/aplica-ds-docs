# Aplica DS — V3

## Context

V3 is the current phase of Aplica DS (2024–present). It is the distribution phase: everything proven in V2 was repackaged so that any team can adopt it without forking or copying internal files.

The two structural changes that define V3:

1. **Package-first** — `@aplica/aplica-theme-engine` is published as a standalone npm package. Consumers install it as a dependency instead of copying source files.
2. **Consumer workspace model** — configuration and data live entirely in the consumer project. The package is a pure engine; it brings no opinions about brand, colors, or typography.

---

## The Great Shift: From Copy to Package

In V2, teams adopted the Theme Engine by copying or forking the repository. Updates required manual merging. V3 replaced this model:

| | V2 | V3 |
|---|---|---|
| Adoption | Copy / fork | `npm install @aplica/aplica-theme-engine` |
| Configuration | In the engine repo | In the consumer project (`aplica.config.mjs`) |
| Updates | Manual merge | `npm update` + migration bundle |
| Schema ownership | Engine-controlled | Consumer can override via `paths.schemasDir` |

## V3 Innovations

### 1. Standalone npm Package

```bash
npm install @aplica/aplica-theme-engine
```

The package exposes:
- `defineThemeEngineConfig()` — public configuration API with full TypeScript inference
- `/config` — importable config helpers
- `/transformers/config` — extensibility hooks for custom transformers

### 2. Consumer Workspace Scaffolding

```bash
npx theme-engine init
```

Interactive wizard that creates:
- `aplica.config.mjs` — project configuration
- `data/` — schema and architecture files
- `dist/` — build output directory

Alternatively, `--template <starter>` skips the wizard.

### 3. Automated V2 Migration

```bash
npx theme-engine migrate:legacy-consumer
```

Three subcommands for safe migration from pre-V3 monolithic projects:

| Subcommand | Purpose |
|------------|---------|
| `analyze` | Reports what needs to change |
| `convert` | Applies the migration automatically |
| `compare` | Diffs the before/after state |

### 4. Figma Integration via `figma:generate`

```bash
npx theme-engine figma:generate
```

Generates and maintains the three files Tokens Studio requires:

| File | Purpose |
|------|---------|
| `data/$themes.json` | Theme configuration for Tokens Studio |
| `data/$themes.engine.json.template` | Template for engine-managed fields |
| `data/$metadata.json` | Token metadata |

Stable IDs via SHA1 of `"group:name"` — no random IDs that force re-sync in Figma. Figma-owned fields (`id`, `$figmaStyleReferences`, `variableIDs`) are preserved on every run.

### 5. Foundation Styles as CSS Classes

V3 graduated Foundation Styles — introduced in V2 2.26.0 — as the primary consumption path for component authors and AI agents:

```bash
# Generated by the engine
dist/css/foundation/{brand}/typography.css
dist/css/foundation/{brand}/elevation.css
```

Each class is a composite: typography classes bundle 7 CSS properties referencing semantic tokens; elevation classes bundle `box-shadow` per level. Values resolve at runtime from the active theme file — theme switching updates them automatically.

### 6. AI Skills Injection Program

```bash
npx theme-engine ai:init
```

Injects editor-specific context files into the consumer workspace:

| Destination | Tool |
|-------------|------|
| `docs/context/` | All AI agents (shared) |
| `.cursor/rules/` | Cursor |
| `.claude/skills/` | Claude Code |
| `.github/instructions/` | GitHub Copilot |

The injected files teach agents which token layer to read, how to map intent to semantic tokens, and when to prefer Foundation Styles over atomic token assembly.

### 8. `theme-engine` — preferred CLI alias (since 3.8.0)

```bash
npx theme-engine init
npx theme-engine ai:init
npx theme-engine build:all
```

`theme-engine` is now the preferred command name for consumer workspaces. The legacy `aplica-theme-engine` name is preserved as a compatibility fallback — existing scripts continue to work without changes.

All active documentation, onboarding flows, and consumer guides standardize on `theme-engine` first. The package name (`@aplica/aplica-theme-engine`) and config filenames (`aplica-theme-engine.config.mjs`) are unchanged.

---

### 7. AI UI Integration Program

A formal contract that specifies how AI agents consume the token system when generating UI:

- **Preferred path**: Foundation Styles (`typography.css`, `elevation.css`) — one class maps to a complete style decision
- **Secondary path**: Semantic tokens (`action.bg.brand.default`) — when fine-grained control is needed
- **Never**: Brand, Mode, or Surface layer tokens — those are engine internals

Seven component archetypes (Button, Dialog, Input, Badge, Select, Card, Tabs) define the canonical token decision model for each component type.

## V3 milestone versions

Current version: **3.24.1**

- **3.24.1** — Documentation patch. The docs installed by `ai:init` and `ai:knowledge` (`knowledge-guide`, `engineering-guide`, `token-concepts`, `components-guide`, `aplica-ui-integration`) now cover the 3.24.0 opt-in opacity families, `alpha` vs `raw`, `opacityStrategy`, `jsonTyped.colorFormat` and `structure.opacityColors`; the engine's version documents were closed at 3.24.0. No generated output changes.
- **3.24.0** — Opt-in opacity families + Dart/Flutter color format. `global.opacityColors` (`brand`, `feedback`, `product`, `function`) adds `semantic.opacity.color.<family>.<item>.<step>`; `global.opacityStrategy: 'rgba-ref'` writes `rgba({base}, {semantic.opacity.alpha.<step>})` with unitless 0-1 `number` alpha tokens so Tokens Studio >= 2.13.0 links color and opacity variables in Figma (CSS/JS/JSON output identical to `modify`); `structure.opacityColors` in a foundation config aliases the families into `foundation.opacity.color.*`; `formatOptions.jsonTyped.colorFormat` (`hex8` | `rgb` | `argb` | `components` | `dtcg`) normalizes colors in `dist/json-typed/` for Dart/Flutter. Everything is opt-in: a workspace that sets none of it keeps byte-identical output (guarded by `test:opacity-contract` against a frozen baseline). New `docs/context/DEPRECATIONS.md` registers compatibility shims for the next major. Canvas-aware dilution guide (`#13`) replaces the original design proposal.
- **3.23.1–3.23.4** — Patch releases: docs for generic alias sections in foundation `structure` (3.23.1, 3.23.2); missing themes and fonts added to playground manifests (3.23.3); `docs/context/ai-ui` now ships in the npm package (3.23.4).
- **3.23.0** — New feature: generic alias pass in foundation. Any `structure` key that declares three fields — `semanticPath`, `type`, and `items` — is processed automatically by `generate-foundation.mjs`, exposing semantic tokens as foundation aliases without engine changes. Example use cases: `fontFamilies`, `lineHeights`, `fontWeights`, `letterSpacing`, or any custom path in `data/semantic/default.json`. Explicitly-handled sections (`bg`, `border`, `txt`, `opacity`, `sizing`, `spacing`, `borderWidth`, `borderRadius`, `typography`, `gradient`) are protected by `EXPLICITLY_HANDLED_SECTIONS` and never processed by the generic pass — fully backward-compatible. Prerequisite: the declared `semanticPath` must exist in `data/semantic/default.json`.
- **3.22.4–3.22.5** — `borderWidth` and `borderRadius` became first-class `structure` keys in foundation configs (handlers + docs).
- **3.22.3** — Fix: CLI was duplicating error output when a script failed with its own message. `runNodeScript` (`index.mjs`) now uses a discriminated catch: `err.status != null` (child ran and exited non-zero) → `process.exit(err.status)` silently (child already printed its error); `err.status == null` (spawn failure) → rethrows to `main()`'s catch so fatal errors are still surfaced. Same fix in `utils/init-helper.mjs` for the playground mode `execFileSync` subprocess. Result: `init` option 3 on an uninitialized workspace now shows `[error] No workspace config found` only, instead of that error plus 2× `"Fatal error: Command failed: ..."`.
- **3.22.2** — Fix: `surface.opacity.color.dark.*` / `surface.opacity.color.light.*` tokens were not inverting when switching light/dark mode in Figma. Root cause: opacity tokens referenced an intermediate chain (`mode.opacity`) with hardcoded paths incompatible with the standard engine schema (`SURFACE_POLARITY_ENABLED=true`). Fix: `generateSurfaceOpacity` rewritten to be schema-aware — when `SURFACE_POLARITY_ENABLED=false`, uses `mode.brand.ambient.contrast.base.{polarity}.background`; when `true`, uses `mode.brand.ambient.contrast.base.{surfaceType}.{polarity}.background`. Each token now uses `$extensions.studio.tokens.modify.alpha` with `space: srgb` and `format: hex` to apply alpha via Tokens Studio. `updateModeFile` cleans up orphan `mode.opacity` tokens from previous syncs. Run `tokens:sync` to apply.
- **3.22.0** — Mode-specific interaction override leaves: `overrides.interaction` preset leaves now support per-mode values. Three formats — all backward-compatible: global (existing behavior, unchanged), mode-specific-both (`light`/`dark` keys in preset with different values per mode), mode-specific-partial (one mode explicit, other auto-generated by the engine). Detection rule: if a preset value contains a `light` or `dark` key → mode-specific, else → global leaf. Consistent with the `{ light, dark }` convention already used in `overrides.grayscale`, `overrides.neutrals`, and `options.txtOnCustomTint`. Eliminates the class of `[override:accessibility]` warnings caused by forcing light-optimized override colors into dark mode. No migration required.
- **3.21.1** — Fix: `sync:architecture` was deleting `data/surface/negative.json` when `surfacePolarity: false` was set in the workspace, removing the Figma "negative" surface collection mode and breaking token references like `surface.opacity.color.dark` / `surface.opacity.color.light` after `tokens:sync`. Fix: `sync:architecture` now writes `surface/negative.json` as a stub with identical content to `surface/positive.json` (opacity values are canvas-ambient and mode-invariant — semantically correct); `generate-figma-theme-files` now includes the `surface/negative` entry in `$themes.json` and `$themes.engine.json.template` even when polarity is disabled. No config changes required.
- **3.21.0** — Patch: `background` interaction override was deriving `txtOn` from the original item's color palette instead of the palette generated from the declared background hex. Fixed in `_collectInteractionOverrideColors` — `leaf.background` is now indexed and `txtOn` uses `bgPaletteScale`. Any config using `background` may see `txtOn` change; declare `txtOn` explicitly to pin a specific tone.
- **3.20.0** — Interaction override leaf extended to 5 fields: `background` (direct surface, `txtOn` auto-computed WCAG AA, `border` derived), `color` (full decomposition pipeline — surface is diluted, not the raw hex), `txtOn` (WCAG-enforced text override — skipped with `[override:accessibility]` warning if fails 4.5:1), `txt` (ambient reading text, requires `generateTxt: true`), `border` (unconditional border override). Valid states: `normal`, `action`, `active`, `focus`. Empty leaf is a parse-time error. 171 new tests; `build:themes` gated behind `test:theme-engine`.
- **3.19.0–3.19.2** — 6 Claude Code slash commands (`/theme-engine`, `/aplica-components`, and 4 utility skills); `ai:init` redesigned to deliver self-contained skills with embedded knowledge (`token-concepts.md`, `engineering-guide.md`) — no external dependencies; `theme-engine` skill detects N1/N2/N3 level and responds accordingly.
- **3.18.0** — `brand-tint` overlap + showroom coverage: `overlap: { level: N }` lets palette surfaces above the threshold skip the brand-tint walk and go straight to the extreme (black or white) set by `colorContrastDecompose` — more editorial and legible on brands with highly saturated palettes; `aplica_ember` is the canonical reference for `overlap: { level: 120 }`; the `aplica_sky`, `aplica_forest`, `aplica_grinch`, `aplica_obsidian` and `aplica_tangerine` configs gain inline documentation for `colorContrastDecompose`
