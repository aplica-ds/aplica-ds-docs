# N2-06 · Responsible Overrides

## Context

The Aplica DS pipeline is sophisticated — but it is not omniscient. There will be cases where the generated behavior is not exactly what a brand needs. The neutral tone came out too cold. The generated gray does not match the warm identity of the brand.

Overrides exist for those cases. But they have a cost — not in tokens, but in maintainability — and a protocol that must be followed.

---

## Concept

### What overrides are

Overrides are configurations in `*.config.mjs` that replace values generated by the default pipeline. You are telling the engine: "For this specific case, ignore the calculated value and use this one instead."

The engine accepts overrides at three points:

**1. Grayscale** — the fixed gray scale  
By default, grayscale is a neutral gray. Brands with warm identities (fashion, food, lifestyle brands) often need slightly yellowed or pinkish grays to maintain visual coherence.

```javascript
overrides: {
  grayscale: {
    light: {
      surface: {
        '5':   '#faf8f5',  // off-white with warm tone
        '10':  '#f5f2ee',
        '140': '#1a1814'   // near-black with warm tone
      }
    },
    dark: { /* same structure */ }
  }
}
```

**2. Neutrals** — the grays derived from the brand color  
By default, neutrals are calculated with 10% of the brand color's chroma. Sometimes that calculation does not produce the desired visual result.

```javascript
overrides: {
  neutrals: {
    brand_primary: {
      light: { surface: { '5': '#fdf4f9' } }  // only the level that needs it
    }
  }
}
```

**3. Interaction states** (since v3.20.0) — specific interaction state overrides for `function` or `feedback` surfaces  
Since v3.20.0, the state leaf accepts five fields. Each affects a different part of the state's visual:

| Field | What it overrides | Contrast check |
|-------|-------------------|----------------|
| `background` | Surface directly via the declared hex. `txtOn` is auto-computed to WCAG AA; `border` is derived from this hex. | `txtOn` always passes AA |
| `color` | The source color that runs through the full decomposition pipeline. Surface is diluted — not the raw hex. | derived by theme strategy |
| `txtOn` | Text/icon on the surface. **Only applied if the value passes WCAG AA (4.5:1).** If it fails, the engine emits `[override:accessibility]` with the exact ratio and preserves the auto-computed value. | enforced |
| `txt` | Ambient reading text on the page canvas. Only relevant when `generateTxt: true` is active in the workspace. | enforced |
| `border` | State border color. Applied unconditionally, no contrast check. | none |

Each leaf must declare at least one field — an empty leaf is a parse-time error. Valid states: `normal`, `action`, `active`, `focus`.

```javascript
overrides: {
  interaction: {
    function: {
      items: {
        primary: {
          states: {
            active: {
              solid: { background: '#C73C9E' }   // brand color directly — txtOn auto WCAG AA
            },
            action: {
              solid: { color: '#0067FF' }         // dilution pipeline — surface is diluted, not raw hex
            },
            focus: {
              solid: { border: '#8B5CF6' }        // border only — no surface or text change
            }
          }
        }
      }
    }
  }
}
```

> **v3.21.0:** When only `background` is declared without an explicit `txtOn`, `txtOn` is derived from the palette generated from the declared background hex — not from the original item color palette. Declare `txtOn` explicitly to pin a specific tone.

**Per-mode format (since v3.22.0):** Preset leaves now accept different values for light and dark mode:

```javascript
active: {
  // Global — same value in both modes (existing behavior, unchanged)
  solid: { background: '#C73C9E' }
}

active: {
  // Mode-specific both — different color per mode
  solid: {
    light: { background: '#C73C9E' },
    dark:  { background: '#AD2385' }
  }
}

active: {
  // Mode-specific partial — light explicit, dark auto-generated
  solid: {
    light: { background: '#C73C9E' }
  }
}
```

Detection rule: if the preset contains a `light` or `dark` key → mode-specific; otherwise → global. All existing flat-leaf configs are unchanged. No migration required.

**Targeting levels (most specific wins):**

| Target | Path |
|--------|------|
| All items in a group, one state | `interaction.{group}.states.{state}` |
| All items in a group, one preset, one state | `interaction.{group}.states.{state}.{solid\|ghost}` |
| One item, one state | `interaction.{group}.items.{item}.states.{state}` |
| One item, one preset, one state | `interaction.{group}.items.{item}.states.{state}.{solid\|ghost}` |

> **Migration note:** The legacy `overrides.interface.function.*` form is still accepted as a compatibility alias. New configs should use `overrides.interaction.*`.

### The mandatory cycle: Study → Test → Document

Before applying any override, follow these three steps:

**Study:** Why does the default value not work? Is the problem real or an aesthetic preference? Sometimes what seems wrong is correct for WCAG and the problem lies in another layer.

**Test:** Apply the override in an isolated environment. Check behavior in both light and dark mode. Confirm that contrast is still adequate in all contexts where the value is used.

**Document:** Record in the config (via comment) or in the theme's CHANGELOG: what the problem was, what the solution was, when it was applied. Undocumented overrides become impossible mysteries to solve months later.

---

### What to NEVER override

**Semantic tokens directly.** The Semantic layer is generated by `sync:architecture` — any manual edit to `data/semantic/default.json` is overwritten on the next execution. If you need to change the behavior of a Semantic token, the change must happen in the schema or in the theme config, not in the generated file.

**Calculated txtOn values without considering contrast.** `txtOn` is calculated to guarantee WCAG AA. If you configure a `txtOn` override in an interaction state leaf and it fails the minimum contrast (4.5:1), the engine emits the named warning `[override:accessibility]` with the exact ratio and the surface, and preserves the auto-computed value — the configured override is silently replaced by the safe value. If you need a different strategy, use `txtOnStrategy: 'brand-tint'` or `'custom-tint'` in the config.

```
⚠ [override:accessibility] action_primary.function.ghost.action.txtOn:
  '#010101' fails WCAG AA (1.05:1) on surface #2d1a0e [dark] — skipped, auto-computed preserved.
```

## Guided example

### Three scenarios: correct, unnecessary, and problematic overrides

---

**Scenario A — Legitimate override**

Artisan food brand. Warm, rustic identity. The default grayscale (cold gray) clashes visually with the entire palette.

*Solution:*
```javascript
overrides: {
  grayscale: {
    light: {
      surface: {
        '5':   '#faf9f7',   // slightly yellowed white
        '10':  '#f5f3f0',
        '20':  '#ebe8e3',
        '140': '#1f1d1a'    // slightly brownish black
      }
    }
  }
}
```

*Documentation in config:*
```javascript
// Grayscale override: brand's warm identity requires grays with
// 2-3% yellow/orange tone. Approved by: DS team, 2026-03.
```

---

**Scenario B — Unnecessary override**

A designer found that level 50 of the primary palette "looked different from what they expected in Figma." They want to override the level 50 surface.

*Analysis:*
- The hex generated by the OKLCh pipeline may be slightly different from the declared hex — this is expected and correct.
- If the contrast is correct and the palette is harmonious, a 1-2 digit difference in the hex is not a problem.
- Overriding to "match Figma" will create a level that departs from the lightness curve of the entire palette.

*Decision:* Do not apply the override. Update Figma to accept the generated value as canonical.

---

**Scenario C — Problematic override**

An engineer wants the txtOn for level 100 of the primary color to always be black (to maintain the brand style) even when white has more contrast.

*Analysis:*
- `txtOn` guarantees WCAG AA. Forcing black over a dark background can fail contrast.
- If the brand wants to maintain color identity in text, the solution is `txtOnStrategy: 'brand-tint'` — the engine will choose the brand tone that passes WCAG.

*Decision:* Use `txtOnStrategy: 'brand-tint'` instead of a manual override. Document if it still does not meet expectations.

## Now you try

Given the scenario below, decide whether an override is necessary and, if so, which one is correct:

> **Personal finance brand.** Primary palette: blue `#2563EB`. The automatically generated neutral has a very noticeable blue tint — in a finance app, where trust is visual, the near-blue neutral looks "not serious enough." The branding team wants neutrals closer to pure gray.

**Expected result:**

Legitimate override. The 10% chroma applied to the vibrant blue results in a neutral with a bluer appearance than desired for a serious finance brand.

Solution:
```javascript
overrides: {
  neutrals: {
    brand_primary: {  // key matching the #2563EB hex in the config
      light: {
        surface: {
          '5':   '#f8f9fa',  // near-pure gray
          '20':  '#e8eaed',
          '60':  '#9aa0a6',
          '100': '#5f6368',
          '140': '#1c1c1e'
        }
      }
    }
  }
}
// Documentation: primary blue neutrals redesigned to more neutral grays.
// Chroma reduced to ~2% vs default 10%.
// Reason: financial brand identity requires visual sobriety.
```
